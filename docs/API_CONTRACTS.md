# Self-Evolving CRM — API Contracts

**Status:** MVP contract v1  
**Base path:** `/api/v1`  
**Content type:** `application/json`, except CSV import (`multipart/form-data`)  
**Source of truth:** This document plus `backend/app/schemas/crm.py`. If either changes, update both in the same pull request.

## 1. Architecture decisions

- CRM definitions are validated JSON metadata, not LLM-generated SQL.
- CRM records are stored in a shared PostgreSQL table with a JSONB `data` column.
- System-owned identifiers, tenant/owner IDs, timestamps, statuses and relationships remain normal database columns.
- Supabase Auth provides user identity. The backend verifies the Supabase JWT and authorizes every CRM-scoped operation.
- All application responses use a consistent JSON envelope.
- API routes are versioned under `/api/v1`.
- AI-generated CRM configuration and evolution changes are drafts until validated and explicitly approved.
- Never expose Supabase service-role credentials to the browser.
- Never execute arbitrary SQL or arbitrary code generated by an LLM.

## 2. Response envelope

### Success

```json
{
  "data": {},
  "meta": {
    "request_id": "req_example"
  }
}
```

For list endpoints, `meta` also includes pagination:

```json
{
  "data": {
    "items": [],
    "total": 0,
    "limit": 20,
    "offset": 0
  },
  "meta": {
    "request_id": "req_example"
  }
}
```

### Error

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "The request is invalid.",
    "details": [],
    "request_id": "req_example"
  }
}
```

Use stable machine-readable error codes. Do not return stack traces, secrets, raw database errors, or provider credentials.

## 3. Authentication and authorization

- Requests to CRM data endpoints require `Authorization: Bearer <Supabase access token>`.
- Verify the JWT server-side using the configured Supabase project/JWKS or supported Supabase verification method.
- Derive `user_id` from the verified token; never trust a user ID supplied by the client to establish ownership.
- Every CRM query must be scoped to the authenticated user's membership/ownership.
- Return `401` for missing/invalid authentication and `403` when authenticated but not authorized.
- Use least-privilege database access. Keep service-role keys server-side only.
- For a hackathon, the initial tenancy model may be one owner per CRM. Keep the schema extensible for teams later.

## 4. Shared CRM configuration schema

A generated configuration is a draft JSON object:

```json
{
  "schema_version": "1.0",
  "name": "Real Estate CRM",
  "industry": "real_estate",
  "entities": [
    {
      "name": "lead",
      "label": "Lead",
      "fields": [
        {
          "name": "full_name",
          "label": "Full Name",
          "type": "text",
          "required": true
        },
        {
          "name": "email",
          "label": "Email",
          "type": "email",
          "required": false
        },
        {
          "name": "status",
          "label": "Status",
          "type": "select",
          "required": true,
          "options": ["New", "Qualified", "Won", "Lost"]
        }
      ]
    }
  ],
  "pipeline_stages": ["New", "Qualified", "Won", "Lost"]
}
```

Allowed field types for MVP: `text`, `textarea`, `email`, `number`, `date`, `boolean`, `select`, `phone`.

Validation rules:
- Entity and field names must be stable machine identifiers: lowercase letters, digits and underscores; start with a letter.
- Entity names and field names must be unique within their scope.
- `options` is required only for `select` and must contain unique non-empty strings.
- Reject unsupported field types, excessively large configurations, duplicate identifiers and reserved system field names.
- Do not permit configuration metadata to define SQL, executable code, arbitrary URLs or arbitrary database table names.
- Validate the configuration before saving it.

## 5. Endpoints

### 5.1 Generate a draft CRM configuration

`POST /api/v1/crm/generate`

Auth: required.

Request:

```json
{
  "prompt": "Create a CRM for a real-estate company that tracks leads, properties and site visits."
}
```

Success `200`:

```json
{
  "data": {
    "configuration": {
      "schema_version": "1.0",
      "name": "Real Estate CRM",
      "industry": "real_estate",
      "entities": [
        {
          "name": "lead",
          "label": "Lead",
          "fields": [
            {
              "name": "full_name",
              "label": "Full Name",
              "type": "text",
              "required": true
            }
          ]
        }
      ],
      "pipeline_stages": ["New", "Qualified", "Won", "Lost"]
    },
    "warnings": []
  },
  "meta": {"request_id": "req_example"}
}
```

The configuration is a draft and is not saved/activated by this endpoint. Return `422` if the generated configuration fails validation after any permitted repair attempt; return `502` for an upstream model/provider failure.

### 5.2 Save a validated CRM configuration

`POST /api/v1/crm`

Auth: required. Success `201`.

Request:

```json
{
  "configuration": {
    "schema_version": "1.0",
    "name": "Real Estate CRM",
    "industry": "real_estate",
    "entities": [
        {
          "name": "lead",
          "label": "Lead",
          "fields": [
            {
              "name": "full_name",
              "label": "Full Name",
              "type": "text",
              "required": true
            }
          ]
        }
      ],
    "pipeline_stages": ["New", "Qualified", "Won", "Lost"]
  }
}
```

Success:

```json
{
  "data": {
    "crm_id": "uuid",
    "name": "Real Estate CRM",
    "status": "active",
    "configuration_version": 1,
    "configuration": {}
  },
  "meta": {"request_id": "req_example"}
}
```

The backend validates the complete configuration, assigns ownership from the verified token and stores it. `crm_id` is a UUID in the actual implementation; `"uuid"` above is illustrative.

### 5.3 List CRMs

`GET /api/v1/crm?limit=20&offset=0`

Auth: required. Success `200`.

`data.items` contains CRM summaries; `total`, `limit`, and `offset` are included. Maximum `limit` is 100.

### 5.4 Get one CRM

`GET /api/v1/crm/{crm_id}`

Auth: required. Success `200`; `404` if missing or not visible to the caller.

Returns the CRM summary, active configuration, and `configuration_version`.

### 5.5 Update a CRM configuration

`PATCH /api/v1/crm/{crm_id}/configuration`

Auth: required. Changes that alter the active CRM are applied only through an approved proposal. This endpoint may update safe descriptive metadata only; for schema/workflow changes, use the evolution proposal flow. Include `expected_version` to detect stale updates. Return `409` on version conflict.

### 5.6 Create a lead/record

`POST /api/v1/crm/{crm_id}/records/{entity_name}`

Auth: required.

Request:

```json
{
  "data": {
    "full_name": "Rahul",
    "email": "rahul@example.com",
    "status": "New"
  },
  "source": "Website"
}
```

Success `201`:

```json
{
  "data": {
    "record_id": "uuid",
    "crm_id": "uuid",
    "entity_name": "Lead",
    "data": {
      "full_name": "Rahul",
      "email": "rahul@example.com",
      "status": "New"
    },
    "source": "Website",
    "created_at": "2026-10-10T10:00:00Z",
    "updated_at": "2026-10-10T10:00:00Z"
  },
  "meta": {"request_id": "req_example"}
}
```

The backend validates `data` against the saved configuration for that entity, enforces required fields and field types, and stores values in the shared records table's JSONB column. `record_id`, ownership, timestamps and CRM/entity identifiers are separate columns.

### 5.7 List records

`GET /api/v1/crm/{crm_id}/records/{entity_name}?limit=20&offset=0`

Auth: required. Return the standard paginated envelope. Default `limit=20`, maximum `100`. Filtering and sorting should be added only after the basic list endpoint works.

### 5.8 Update a record

`PATCH /api/v1/crm/{crm_id}/records/{entity_name}/{record_id}`

Auth: required. Request:

```json
{
  "data": {
    "status": "Qualified"
  }
}
```

Merge only allowed fields after validating them against the current configuration. Return `404` for records not visible to the caller.

### 5.9 Delete a record

`DELETE /api/v1/crm/{crm_id}/records/{entity_name}/{record_id}`

Auth: required. Success `200` with `data.deleted=true`. Use soft-delete if practical for the MVP.

### 5.10 Import CSV leads/records

`POST /api/v1/crm/{crm_id}/records/{entity_name}/import`

Auth: required. Content type: `multipart/form-data`, field name `file`.

Success `200`:

```json
{
  "data": {
    "imported": 18,
    "skipped": 2,
    "errors": [
      {"row": 4, "code": "INVALID_EMAIL", "message": "Email is invalid."}
    ]
  },
  "meta": {"request_id": "req_example"}
}
```

Enforce file size and row-count limits. Validate every row. Never trust CSV values as formulas, HTML or executable instructions. Person 4 owns ingestion; Member 2 owns the persistence primitives.

### 5.11 Create a workflow

`POST /api/v1/crm/{crm_id}/workflows`

Auth: required.

Request:

```json
{
  "name": "Follow up after new lead",
  "trigger": {"event": "record.created", "entity": "lead"},
  "actions": [
    {
      "type": "create_follow_up_task",
      "delay_hours": 12
    }
  ],
  "enabled": false
}
```

Success `201`: returns `workflow_id`, `status`, and validated workflow configuration. Workflows generated by AI start disabled/draft until authorized. Only allowlisted trigger/action types may run; do not execute generated code.

### 5.12 Get analytics

`GET /api/v1/crm/{crm_id}/analytics`

Auth: required. Success `200`:

```json
{
  "data": {
    "total_leads": 120,
    "qualified_leads": 40,
    "won_leads": 12,
    "conversion_rate": 0.10,
    "by_source": [],
    "by_stage": []
  },
  "meta": {"request_id": "req_example"}
}
```

Define conversion rate consistently: `won_leads / total_leads`, for the same CRM and reporting period. If there are no leads, return `0`, not `NaN` or infinity.

### 5.13 Generate an evolution proposal

`POST /api/v1/crm/{crm_id}/evolution/proposals`

Auth: required.

Request:

```json
{
  "objective": "improve_follow_up"
}
```

Success `201`:

```json
{
  "data": {
    "proposal_id": "uuid",
    "status": "pending",
    "summary": "Follow up sooner after a demo.",
    "proposed_change": {
      "type": "workflow.update",
      "workflow_id": "uuid",
      "delay_hours": 12
    },
    "evidence": []
  },
  "meta": {"request_id": "req_example"}
}
```

AI suggestions must cite computed metrics or observed events as evidence. A proposal is not applied when created.

### 5.14 Approve an evolution proposal

`POST /api/v1/crm/{crm_id}/evolution/proposals/{proposal_id}/approve`

Auth: required. Request:

```json
{
  "expected_status": "pending"
}
```

Success `200`: returns the proposal with `status: "applied"` if validation and authorization succeed. Approval must be explicit and recorded in an audit log. Revalidate at approval time, use version checks, and make repeated approval requests idempotent where possible. Reject stale proposals with `409`.

### 5.15 Reject a proposal

`POST /api/v1/crm/{crm_id}/evolution/proposals/{proposal_id}/reject`

Auth: required. Request:

```json
{
  "reason": "Not appropriate for our sales process."
}
```

Success `200`: returns `status: "rejected"`.

## 6. Common errors

- `400 BAD_REQUEST`: invalid business operation.
- `401 UNAUTHENTICATED`: token missing or invalid.
- `403 FORBIDDEN`: caller lacks permission.
- `404 NOT_FOUND`: resource missing or not visible to caller.
- `409 CONFLICT`: stale configuration/version or incompatible state transition.
- `413 PAYLOAD_TOO_LARGE`: import exceeds limits.
- `422 VALIDATION_ERROR`: request or generated configuration fails validation.
- `429 RATE_LIMITED`: rate limit exceeded.
- `502 AI_PROVIDER_ERROR`: upstream model provider failed.
- `500 INTERNAL_ERROR`: unexpected failure; do not expose internals.

2. Implement Supabase JWT verification and CRM ownership checks.
3. Implement CRM create/get/list and dynamic record CRUD.
4. Implement draft generation with a mock provider, then connect the selected LLM.
5. Implement CSV import and workflow execution using allowlisted actions.
6. Implement analytics and evolution proposals with human approval.
7. Generate and inspect `/openapi.json`; update this document and tests in the same PR when contracts change.

## 8. Definition of done

- Requests and responses match the documented models.
- All CRM-scoped endpoints enforce authentication and ownership.
- No secrets are committed or sent to the frontend.
- AI-generated configurations/actions are validated before persistence or execution.
- Tests cover success, validation failure, unauthorized access, missing resources and version conflicts.
- `docs/API_CONTRACTS.md` and generated OpenAPI documentation stay aligned.
